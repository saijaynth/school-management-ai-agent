1. Introduction
This manual explains how to use the School Management database. The database stores
everything a school needs to run day to day: users and roles, classes and sections,
subjects, classrooms, timetables, student and faculty attendance, leave requests,
homework, assignments, exams, marks and progress reports.
The database supports three roles:
Note: the roles  table controls what a person may do inside the school application. It is
separate from PostgreSQL login roles (see Section 11.4).

3.1 Key relationships
Every user belongs to one role: users.role_id  references roles .
Every person has exactly one profile row, linked by user_id : admins , faculty  or
students .
A section belongs to a class and an academic year, and has a class teacher
( sections.class_teacher_id  references faculty ).
A student belongs to one current section ( students.section_id ).
course_assignments  ties together a section, subject, faculty member and classroom.
timetable  places a subject, faculty member and classroom into a period on a
weekday for a section.
Attendance, homework, assignments and marks all point back to students or faculty
through foreign keys.
exams  belong to a class; exam_schedules  give each subject its date, room and
maximum marks; marks  hold each student's result per scheduled subject.

Generate reports for a new exam once all marks are entered (replace 2 with the exam_id
and 1 with the admin user_id):
INSERT INTO progress_reports (student_id, exam_id, total_max_marks, 
total_obtained, percentage, generated_by)
SELECT m.student_id, es.exam_id, SUM(es.max_marks), SUM(m.marks_obtained),
       ROUND(100 * SUM(m.marks_obtained) / SUM(es.max_marks), 2), 1
FROM marks m JOIN exam_schedules es ON es.exam_schedule_id = 
m.exam_schedule_id
WHERE es.exam_id = 2
GROUP BY m.student_id, es.exam_id;
UPDATE progress_reports pr
SET grade_id = (SELECT g.grade_id FROM grade_scale g WHERE pr.percentage 
BETWEEN g.min_percent AND g.max_percent)
WHERE pr.exam_id = 2;
UPDATE progress_reports pr SET class_rank = r.rk
FROM (SELECT report_id, RANK() OVER (ORDER BY percentage DESC) AS rk
      FROM progress_reports WHERE exam_id = 2) r
WHERE pr.report_id = r.report_id;
UPDATE progress_reports SET is_published = TRUE WHERE exam_id = 2;
Also insert the subject lines into progress_report_items  (one row per subject per
report) so students can see the subject-wise breakdown.

10.2 Indexes
Indexes exist on the foreign keys most used in reports (for example student, section,
attendance date, leave status, marks by student). Unique constraints automatically create
their own indexes. Run \d tablename  to see all indexes of a table.
11. Maintenance
11.1 Backup
Run from the operating system command line, not inside psql:
pg_dump -U postgres -n school school_db > school_backup.sql
Schedule this daily, and keep copies on a different drive or machine.
11.2 Restore
psql -U postgres -d school_db -f school_backup.sql
Restore into an empty or fresh schema. If the school  schema already exists with data,
drop it first or you will see duplicate object errors.
11.3 Reset to sample data
Re-run school_management_postgres92.sql . This deletes all current data in the school
schema and recreates the sample records. Back up first if you need to keep anything.
11.4 Database logins and permissions
The Admin, Faculty and Student roles are application roles. To also restrict access at
database level, create PostgreSQL login roles. Example for a read-only reporting user:
CREATE ROLE report_user LOGIN PASSWORD 'ChangeMe#123';
GRANT USAGE ON SCHEMA school TO report_user;
GRANT SELECT ON ALL TABLES IN SCHEMA school TO report_user;
Example for an application user that can read and write data:

11.5 Security recommendations
Never store plain-text passwords. Store a bcrypt or argon2 hash in password_hash .
Do not let students or faculty connect directly with the postgres superuser. Use the
application layer or limited login roles.
Student and faculty queries must always filter by the logged-in person (username,
student_id or faculty_id) so they only see their own data.
Take regular backups and test a restore at least once a term.
PostgreSQL 9.2 no longer receives security updates. Plan an upgrade to a supported
version when possible. The script can be used on newer versions as well.
11.6 Year-end routine
1. Insert the new row in academic_years  and set the old one to is_current = FALSE .
2. Create the new year's sections .
3. Move students to their new sections: UPDATE students SET section_id = <new
section> WHERE student_id = <id>;
4. Create new course_assignments , timetable  rows and exams.
Past attendance, marks and reports stay in the database for history.
